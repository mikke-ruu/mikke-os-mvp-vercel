# mikkeOS セレクトショップ／提携モデル 設計メモ

作成日: 2026-07-16
作成: Claude (Fable) — 全体設計の判断担当
状態: 構想の設計判断まで完了。実装未着手（Page PG-3以降＋Team Works本接続後）。

Page所有事業者が、提携した別事業者の商品・サービスを自社ページに掲載し、
販売・発送・報酬までを回すモデル。**複数アプリにまたがるため独立docsにした。**

関連: `MIKKEOS_PAGE_IMPLEMENTATION_PLAN.md` / `MIKKEOS_TEAM_WORKS_PROJECTS_PLAN.md`
     / `MIKKEOS_MANAGER_INTEGRATION_PLAN.md` / `MIKKEOS_MONETIZATION_AND_PRICING.md` 7章

## 1. 対応できる業態（同一構造で回る）

```text
セレクトショップ（ハンドメイド作家の商品を集めて販売）
占い業（占い師を掲載して予約を受ける）
ワークショップ業（講師を掲載して申込を受ける）
地域の商店街（地域店舗を集めて掲載）
```

営業が得意な事業者と、実務・製作が得意な事業者がwin-winで進む構造。

## 2. 登場人物とアプリの対応

| 登場人物 | 役割 | 使うアプリ |
|---|---|---|
| Page所有者（例: アリサ） | 掲載・集客・販売者本人・報酬支払 | Page＋Team Works（両方の団体課金） |
| 提携店舗（例: A/B/C） | 商品・サービスの提供者 | Item Studio（自分の商品）＋Manager（通知）＋worker portal |
| お客様 | 購入者 | 公開Pageのみ（mikkeアカウント不要） |

Team Worksのラベル替えで成立する（`labelSettings`/`featureSettings`/`templateKey`）:

```text
clients(学校)          → お客様
workers(会話パートナー) → 提携店舗 / 占い師
sessions(授業)         → 鑑定・ワークショップ等
assignments(シフト割当) → 発送依頼・予約割当
payouts(パートナー報酬) → 提携店舗への報酬
reports(授業報告)      → 発送報告（＋追跡番号フィールドを追加）
```

Team Worksの汎用化（「日本語会話専用に固定せず小規模チーム運営SaaSとして汎用化」）が
ここで効く。新アプリを作らない。

## 3. 2つのパターン（掲載関係と報酬関係は別物）

```text
A. 掲載するだけ
   Page CMS掲載（PG-4: mikkeID掲載依頼→承認）のみ。お金も仕事も発生しない。
   → 掲載関係のみ

B. 仕事に繋がる
   掲載＋販売委託。Team Worksのworker・payoutを伴う。
   → 掲載関係 ＋ 報酬関係
```

同一の提供者が両方の関係を同時に持つ。UX上は1回の承認へ統合する（下記4章）。

## 4. 提携の承認（受信箱・条件は「提示→承認」の一方向）

条件を双方が独立に設定すると矛盾するため、**Page所有者が条件を提示し、
提供店舗が承認/辞退する一方向**にする（2026-07-16 Fable判断）。

Manager受信箱（`MIKKEOS_MANAGER_INTEGRATION_PLAN.md` 2.5章）に載る:

```text
アリサのセレクトショップから提携のご依頼が届いています

☑ 商品を掲載する（Item Studio）
☑ 販売を委託する
   条件: 売価から20%（あなたの受取＝表示価格の80%）

［承認］［辞退］
```

掲載依頼（PG-4）と販売委託（報酬条件）を1つの承認payloadにまとめる。

## 5. 販売フロー（確認型・2026-07-16確定）

**即時決済にしない。在庫確認→確定→決済の確認型にする。**

```text
1. お客様が公開Pageで商品・サービスを見る
   （在庫切れは自動で掲載停止 ← 参照型＝コピーしない原則の効果。実装不要で成立）
2. お客様が申込（Pageの申込ブロック）
3. Page所有者が在庫・可否を確認 → 確定
4. 確定後に決済（Page所有者のStripeで満額徴収）
5. 提携店舗のManagerへ通知 →「発送してください」/「予約が入りました」
6. 提携店舗がworker portalで発送先情報・販売商品を確認
7. 発送後、追跡番号を追加して報告（Team Works reports）
8. お客様に届く
9. レビューが届く（下記7章）
10. 締め日・支払日に沿ってPage所有者から提携店舗へ振込（Team Works payout）
```

確認型を採る理由:

```text
- 在庫引当の同時実行問題（オーバーセル）を業務プロセスで回避できる。
  一点物のハンドメイドで特に重要。
- 実際のネットショップ運営がこの形（在庫切れ時はお客様へ連絡）で回っている。
- 事前に「在庫確認後に確定」と注釈しておけばトラブルにならない。
- 副次効果: 実装が軽い。Pageは「申込ブロック＋確定後の決済リンク」でよく、
  埋め込みチェックアウトの複雑さが不要。Orderの確認型フローと同型。
```

将来、即時決済を足す場合は在庫引当の設計が別途必要（現時点では作らない）。

## 6. 手数料（2026-07-16確定）

```text
- Page所有者が自由に設定できる。
- 方式は選択制: 「売価から◯%差し引く」または「売価に◯%／◯円上乗せする」。
- 単位は % または 固定額（例:「1000円乗せる」）。感覚的に分かりやすいものにする。
- 条件は提携の承認時に提示→承認（4章）。
- 上乗せ方式では、同じ商品が提供店舗の直販と価格が異なる。
  これは卸/小売として正常（お客様がどこで買いたいかを選ぶ）。
論点（未決）: 上乗せ方式では提供店舗が表示価格を制御できないため、
  ブランド価格の毀損がありうる。店舗側が上限（例: 上乗せは20%まで）を
  条件に付けられるようにするか要検討。
```

## 7. レビュー（2026-07-16確定・2設問式）

1回の投稿を2つの宛先へ振り分ける。**星（点数）は付けない。**

```text
「商品（サービス）はどうでしたか？」 → 提供店舗（例: 店舗A）のStoryへ
「ご利用店舗はどうでしたか？」       → Page所有者（アリサショップ）のStoryへ
```

星を使わないのは `Mikke_OS_構想整理_2026-06-19.md` 14章「避けたいもの: レビュー点数だけの
競争／人気順位／ランキング」と一致する。作り手の実績は作り手のStoryへ、店の評判は店の
Storyへ帰属させる。

```text
論点（未決）: レビューの公開可否を誰が持つか。既存Storyは「本人が公開してよいものを出す」
  方針（無料=レビュー件数または一部／Plus=全レビュー表示）なので、それに従うなら整合する。
```

## 8. 返品・キャンセル・支払サイクル（2026-07-16確定）

```text
- キャンセルポリシーはPage所有事業者が自分で設定し、公開Pageに掲載する。
  mikkeは関与しない（料金正典0章）。テンプレートの用意までがmikkeの範囲。
- 締め日・支払日を設定し、それに沿ってpayoutを実行する。
  → 発送直後に即振込しないため、返品・キャンセルとの整合が取れる。
- Team Worksのpayoutに締め日・支払日サイクルの設定が必要（小さな追加）。
```

## 9. 必須前提（着手条件・重要）

```text
worker portalのアクセス制御をRLSで担保すること。

設計は当初から正しい（提供店舗は自分の担当分だけを見る。Amazonの出品者画面と同じ）。
問題は担保の仕方であり、UIのフィルタリングだけでは不十分。DB層のRLSで強制する。

理由: worker portalに載るのはお客様の発送先情報（氏名・住所・電話＝個人情報）で、
      提携店舗A/B/Cはそれぞれ別事業者（他人）である。店舗Aが店舗Bの注文・顧客情報を
      読めてはならない。

現状: 「Team Worksのworker/clientポータルのデータアクセス制御の深い監査は未実施」が
      既知debtとして記録されている（localStorage段階のため優先度低としていた）。
      → このモデルの着手条件として優先度を格上げする。

やり方は既に確立済み: Fund F5-aのRLS否定test（owner／別authenticated actor／anonの
3者で読めないことを実証）と同じパターンを worker portal に適用する。
```

  - DESK: 売上（お客様の支払い）／経費（提携店舗への報酬）

  4. レビューの2設問→2宛先の振り分け

## 11. 成長ループ（この構想の戦略的価値）

```text
Page所有者がセレクトショップ開業
 → 提携店舗A/B/Cを誘う
 → A/B/Cは【無料】でmikkeに参加（Manager＋Item Studio）
 → 仕事が来る体験をする（発送依頼→報告→レビュー）
 → Storyが育つ
 → 自分もPageを持ちたくなる → 新しいセレクトショップ主が生まれる
```

これはユーザーがマルシェで既に行っていること（出店者を集める）のデジタル版であり、
入口戦略（マルシェ出店メンバーにMarketNoteを配る）と同じ構造。
誘われた側が無料で価値を体験できることが、ループ起動の条件。
