# mikkeOS 収益化・料金方針（現行集約）

作成日: 2026-07-16
作成: Claude (Fable) — 全体設計の判断担当

原典: `G:/Musubiプロジェクト/Mikke OS/アオイ回答_収益化提携成長方針_2026-06-19.md`
     ＋ 各アプリ正式構想書の料金記述 ＋ 2026-07-16のユーザー確定。

このdocsは、散在していた収益化方針を1枚に集約し、方針書より後に生まれたアプリ
（Session / Item Studio / Team Works / Fund / Academy / Community / Page / Manager）
まで含めて整合させた「料金の正典」です。課金機能は各アプリのSupabase本接続フェーズで
実装しますが、その時に参照する方針をここで固定します。**今はポリシーの確定であり、
課金機能の実装は含みません。**

## 0. 大原則（不変）

```text
- 広告なし（Storyは信用ページ。広告で価値が落ちる）。
- 「使えないから課金」ではなく「もっと整えたい・見せたい・残したい」から課金。
- MVPは段階を増やさない（個人はFree/Plusの2段階から）。
- 意思決定・価格・仕様の決定権は株式会社OJAS側が持つ（意見はもらう、決定権は渡さない）。
- 【関与しない原則・2026-07-16確定】mikkeはアプリという場所・ツールを提供するだけ。
  利用事業者の事業運営には一切関与しない。使い方は利用事業者に完全に任せる。全部が任意。
  → mikkeは利用事業者とその顧客の間の取引・トラブル・運営判断の責任を負わない。
  → この原則が、以下のお金のモデル全体を規定する。
```

## 1. お金のモデル（2026-07-16に単純化・最重要）

**mikkeの収益は①だけ。** それ以外のお金には触れない。

```text
① mikke利用料   利用者 → mikke（mikkeの唯一の収益）
     機能提供の対価。個人Plus月額／団体アプリの個別課金／
     Academy初期設定費+月会費／テンプレート販売／導入サポート。
     Stripeで課金（13章）。

② 利用事業者のお金   事業者の顧客 → 利用事業者（mikkeは一切関与しない・手数料0%）
     Order代金／Fund応援／Academy受講料・更新料・キット／Session予約／
     Community会費 → 本人の外部決済リンク（本人のStripe/Square/STORES等）。
     さらに: Page上の掲載→成約→成約手数料も、利用事業者自身の②の売上。
     mikkeはそこから取らない（7章）。
```

かつて「③マッチング層（Partners/Connectでmikkeが成約手数料を取る）」を置いていたが、
2026-07-16に**解消**した。理由: Partners/Connectはmikkeが1事業者としてPageで作るものであり、
mikkeOSのプラットフォーム機能ではない（7章）。成約手数料機能はPageの有料機能として
他事業者にも提供し、**mikkeはその機能利用料（①）を取るだけ**で、成約金額からは取らない。

これにより、mikkeが資金を預からない／GMVから取らないという原則が全層で貫かれる
（信用維持・資金移動業リスク回避・関与しない原則と一致）。

## 1.5 課金するのは「オーナー1人」原則（2026-07-16確定・全団体アプリ共通）

団体アプリの利用料（①）を払うのは、そのアプリを立ち上げたオーナー1人だけ。
オーナーが招いた側（巻き込まれる側）はmikkeへの支払いが一切ない。

```text
アプリ         払う人（①）           無料で参加する側
Event          主催者                出店者・参加者
Team Works     オーナー              worker（パートナー）・client
Community      主催者                会員
Fund           プロジェクト所有者     応援者・参加者
Page           Page所有者            掲載される提供者・お客様
セレクトショップ Page所有者(＋TeamWorks) 提携店舗A/B/C
```

理由: 招いた側が有料だと誰も参加せず、成長ループが起動しない
（`MIKKEOS_SELECT_SHOP_MODEL.md` 11章）。巻き込まれる側は無料で価値を体験し、
やがて自分がオーナー側に回る、という循環を守る。

補足（オーナーが参加者から会費を取りたい場合）:

```text
オーナーが会員・参加者から会費を徴収したいときは、オーナー自身が別途徴収する。
これは②（利用事業者のお金・mikkeは関与しない・外部決済）に落ちる。
例: Community月会費、有料サロン。mikkeはその会費に手を出さない。
```

## 2. ティア構成（2026-07-16確定）

```text

個人 Plus      増やす・強く見せる・お金を分析する（月額）
団体（個別課金） 他人を巻き込む機能。アプリごとに個別課金（束ねない・2026-07-16確定）。
               各団体アプリに1ヶ月無料トライアルあり（下記6章）。
               ※個別プロダクトとして課金するが、Stripe上は1利用者=1請求に
                 まとめられる（請求書は1本・明細で各アプリを表示。下記13章）。
Academy        位置づけは他の団体アプリと同じ。ただし初期設定料金 + 月会費で、
               無料トライアルなし（下記5章）。
```

## 4. 無料 / 有料の境界線（課金軸＝「誰を巻き込むか」）

機能の高さではなく「誰を巻き込むか」で切る。原典の思想と実装状態に最も素直。

```text
🟢 無料（個人が1人で使う分）— 絶対に絞らない
   MarketNote → 活動ログ → Story → DESK が無料で1周回りきる（原典14章の勝ち筋）。
   Manager（HOME）も無料。1人で記録・整理・見せるまで全部無料。

🟡 個人有料（Plus）— 「増やす・強く見せる・お金を分析する」
   保存上限の解放、独自URL・カスタムデザイン・SEO（Story強化）、DESK集計期間。
   使えなくする課金ではなく、育った人が整えたくなる課金。

🔵 団体有料（別課金）— 「他人を巻き込む機能」
   Event（出店者募集）・Team Works（チーム）・Community（会員）・Page（公開HP）。
   1人で使う分には発生せず、人を集める側だけが払う。原典6章のEvent別課金の理由
   「主催者は価値の感じ方が違う」を後発3アプリにも適用。

⚪ 取引手数料はPartners/Connectだけ（ユーザー自身の売上には手を出さない）
```

## 5. Academy 特例（2026-07-16確定）

```text
【2026-07-16修正】Academyの位置づけは他の団体アプリと同じ（特別なティアではない）。
違うのは料金の形だけ:
  - 初期設定料金（初回）
  - 月会費（継続利用）
  - 無料トライアルなし

初期設定料金を設ける理由:
  - セッティングをしっかり行う必要がある（既存の講座システムからの乗り換えもあるため）。
  - 認定講座ビジネスは利益率が良いため、単価を高めに設定できる。

教科書との関係（誤解の訂正）:
  - 認定講座構築のビジネス教科書は「必須のセット」ではない。
    教科書を読んでAcademyを使ってもよいし、使わなくてもよい。
  - Academyは「認定講座を作った後、それを運営していくためのアプリ」。
    教科書に依存しない。既存講座システムからの乗り換え先にもなる。

受講料・更新料・キット仕入れは②（利用事業者のお金・mikkeは関与しない）。
```

## 6. 団体1ヶ月無料トライアル（2026-07-16確定）

```text
団体プラン（Event/Team Works/Community/Page/Fund）は各アプリ初月無料。
Academyは対象外（初期設定費用があるため。4章）。
狙い: 使い勝手が良ければそのまま継続。
実装メモ: トライアルは「そのアプリを団体として使い始めた日」を起点に月単位で判定。
  個別課金なのでトライアルもアプリごと。乱用防止（1団体で同一アプリのトライアル
  再取得を防ぐ）は課金実装時に考慮。起点の記録先はorganization相当に置く。
  課金機能自体は各アプリのSupabase本接続フェーズで実装するため、現段階はポリシー確定のみ。
```

## 7. Partners / Connect と「成約手数料機能」（2026-07-16・重要な整理）

### 7.1 Partners/Connectはmikkeの1事業であって、OSの機能ではない

```text
- Partners（企業・主催者向け）/ Connect（一般利用者向け）は独立アプリにしない。
- mikke（OJAS）が「1事業者として」Pageを使って作りたいもの。
  つまり他の利用事業者と同じ立場でPageを使うだけ。OSのプラットフォーム機能ではない。
- したがってmikkeOSが成約金額から手数料を取る仕組み（旧③層）は存在しない。
  Partners/Connectで発生する成約手数料は、mikkeの「1事業者としての②の売上」。
```

### 7.2 成約手数料徴収機能 = Pageの有料機能として全事業者へ提供（新方針）

Pageを使う他の事業者も同じ機能を使えるようにし、Page上で広告業・紹介業を営めるようにする。

想定フロー（ユーザー提示・2026-07-16）:

```text
1. お客様がPageのサイトを見に来る
2. 掲載されている提供者（例: 占い師）を利用する
3. お客様が支払う → Page所有事業者のStripeで満額を徴収
4. 提供者への報酬をTeam Worksで決めておく
5. 後日、事業者が提供者へ振り込む（Team Worksのpayout=パートナー報酬で管理）
→ 事業者の取り分（マージン）が実質の「成約手数料」
```

**重要: この形なら Stripe Connect は不要。**

```text
- Page所有事業者が販売者本人（merchant of record）として、自分の通常のStripeで徴収する。
- 提供者への支払いは事業者→提供者の外注費。Team Worksの既存payout（パートナー報酬）で管理できる。
- mikkeは決済に一切触れない（0章 関与しない原則）。資金移動業の論点が発生しない。
- mikkeが取るのは Page（＋Team Works）の利用料だけ（①）。マージンからは1円も取らない。
```

料金上の位置づけ: 有料機能（Plus案件）。利用条件はその事業者がStripeを契約していること。

狙い（ユーザー判断）:

```text
- Pageを使って広告業・紹介業を営む事業者が増える → 離脱が減る（粘着性が上がる）。
- 他のホームページ制作システムとの明確な差別化になる
  （単なるHPビルダーではなく「紹介して手数料を得られるHP」）。
```

料金設計との噛み合い: このモデルを回すには Page（掲載・決済）＋ Team Works（報酬・振込管理）の
両方が要る。**個別課金の方針と自然に噛み合い、1ユースケースで2アプリの団体課金が発生する。**

責任範囲: この形ではPage所有事業者が販売者本人になる（お客様との契約・表示・返金対応等は
その事業者の責任範囲）。mikkeは関与しない（0章）。

### 7.3 必要になる機能（設計は今後相談・未決A）

```text
- Page: 決済・申込ブロック（事業者のStripe決済へつなぐ新しいブロック種別）＋ 成約の記録。
  → Pageの基本ブロック（見出し/文章/画像/ボタン/フォーム/区切り）に加わる有料ブロック。
    Stripe連携が要るためPG-3以降（Supabase接続フェーズ）が現実的。
- Team Works: 掲載提供者をworkerとして報酬設定・payout管理（既存機能の再利用でよい）。
- Page ↔ Team Works の紐づけ（要設計）:
    掲載関係（PG-4のmikkeID掲載依頼→承認）と
    報酬関係（Team Worksのworker・payout）は別物。この2つをどう結ぶかが設計の肝。
- 収支はDESKへ（売上=お客様の支払い、経費=提供者への報酬）。
  既存のActivity Log変換ルール（金額は強制private）に乗る。
```

## 8. 独自ドメイン方針（2026-07-16確定・持ち込み式）

```text
- mikkeはドメインを取得・契約・更新・解約しない。「使えるだけ」の形にする。
- ユーザーが自分で取得したドメインを、mikkeのホスティングへ向ける（DNS向け先を
  受けるだけ）。取得・課金・解約の面倒をmikkeが持たない。
- これによりPage PG-5の独自ドメインは「持ち込みドメインのマッピング受け入れ」に単純化。
  ドメイン代の転嫁・マージンは発生しない（ユーザー実費・mikke外）。
```

## 14. 解約・支払い停止時の挙動（2026-07-16方針確定・詳細は実装時）

```text
【方針】解約は自由に行える。全部が任意。
mikkeはアプリという場所・ツールを提供するだけで、利用事業者の事業運営には
一切関与しない（0章 関与しない原則）。

したがって:
  - 解約による利用事業者の顧客・会員・応援者への影響は、利用事業者の責任範囲。
    mikkeがそれを肩代わりしたり、解約を思いとどまらせる設計にはしない。
  - 「解約させない仕組み」「引き止め」は作らない。自由に出入りできることを優先する。

【mikkeが用意するもの】アナウンスと動線（要設計・実装時）:
  - 停止前の事前アナウンス（いつ止まるか）。
  - 停止後の状態表示（何が止まり、データはどうなるか）。
  - データ保全期間と、再開したときに戻せるか否かの明示。
  - 解約・再開の導線を分かりやすく置く（隠さない）。
公開面（Page）が停止したときの見え方も、上記アナウンスの一部として設計する。
どう運用するか（止める前に自分の顧客へ告知する等）は利用事業者の判断に完全に任せる。
```
