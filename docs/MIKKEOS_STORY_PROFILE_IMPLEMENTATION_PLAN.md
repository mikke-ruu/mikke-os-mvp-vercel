# mikkeOS Story Profile Implementation Plan

作成日: 2026-07-09

このdocsは、mikkeOSの `/story` を「公開Activity Log一覧」ではなく、QRで共有できる名刺型ミニホームページとして再設計するための実装方針メモです。

## 1. Storyの位置づけ

Storyは、本人や事業者が外部に見せるための公開プロフィールです。

役割:

- 名刺代わりになる自己紹介ページ。
- 今の活動内容をまとめるミニホームページ。
- 作品、実績、レビュー、依頼導線、外部リンクをまとめる場所。
- QRコードで相手に見せたり、URLで共有したりできる場所。

Storyは、細かな行動ログをそのまま時系列で見せる場所ではありません。

そのため、Phase 4で使っていた `Story対象` という言葉は、通常表示では `Story素材候補` として扱います。Activity Logの1件1件を自動公開するのではなく、本人が公開してよい情報だけをStory Profileに採用します。

## 2. スマホ表示の理想構成

参考画像の方向性をもとに、スマホでは以下のような構成を目指します。

```text
上部プロフィール
タブ / ショートカット
活動サマリー
作品ポートフォリオ
口コミ
ご依頼・リンク
公開中の講座 / イベント
つながるボタン
QRコード
```

トップの印象は、SNSのプロフィールよりも「仕事用の名刺ページ」に近いものにします。

## 3. 上部プロフィール

表示したいもの:

- プロフィール画像。
- 表示名。
- 任意のハンドル名。
- 肩書きまたは活動名。
- 短い紹介文。
- 活動エリア、オンライン対応などの公開可能な情報。
- 得意なことタグ。
- 受付中ステータス。

得意なことタグ:

- 最大4個。
- 1個あたり短い文言にする。
- 目安は10から12文字程度。
- 例: `講座運営`, `マルシェ主催`, `制作相談`, `ブランド設計`

Mikke IDについて:

- 公開Storyには、内部管理用のMikke IDを表示しません。
- お客さんには関係が薄く、検索や悪用の入口になり得るためです。
- 番号表示が必要な場合も、内部IDと結びつかない任意の公開用番号として別管理にします。

## 4. 受付中ステータス

受付中ステータスは、Story側で手入力するより、各アプリ側の受付状態を元に自動反映する方針にします。

理由:

- 本当は受付中なのにStoryを更新し忘れる事故を避ける。
- 受付停止中なのにStoryだけ受付中のままになる事故を避ける。
- Order / Session / Academy / Event / Community などの公開フロントと状態を合わせる。

想定例:

```text
制作依頼 受付中
個別相談 受付中
講座 受付中
イベント 募集中
コミュニティ 募集中
現在受付停止中
```

運用方針:

- アプリ側の受付ステータスを正とする。
- Story側では「表示する / しない」を選べる。
- 表示ラベルは本人が調整できるようにする。

## 5. 活動サマリー

Storyに出す実績は、細かな行動ログではなく、集計された数字を中心にします。

表示例:

```text
出店・主催 20回
受注 30件
レビュー 50件
セッション 18回
講座開催 8回
販売数 50件
イベント開催 6回
コミュニティ運営 3件
```

重要な方針:

- 出店予定やスケジュールは自動公開しない。
- 「いつ、どこで、何をするか」は行動パターンの推測につながるため、初期状態では出さない。
- MarketNoteを出店以外に使う人もいるため、ラベルは固定しない。
- 例: `出店回数` ではなく、ユーザーが `イベント参加`, `活動回数`, `出店・主催` などに変えられるようにする。

活動サマリーは、Activity Logや各アプリの記録から作れる可能性があります。ただし、Storyに出すかどうかは必ずStory設定のON/OFFで制御します。

## 6. 作品ポートフォリオ

Item Studioは、商品や作品を登録する場所です。

Storyでは、Item Studioに登録された作品をすべて自動表示するのではなく、本人が見せたいものだけを選んでポートフォリオとして表示します。

表示方針:

- 正方形の3列グリッドを基本にする。
- 画像、タイトル、カテゴリラベルを表示する。
- 表示順を並べ替えられるようにする。
- Item Studioから選択できる。
- Story側で手動追加もできる。
- 各作品ごとに表示ON/OFFを持つ。

作品カードの想定項目:

```text
画像
タイトル
ラベル
説明
リンク
表示ON/OFF
表示順
Item Studio由来か手動追加か
```

販売記録はDESK対象であり、Storyの作品ポートフォリオには直接出しません。

## 7. 口コミ

Storyの口コミは、星評価ではなく、短いレビューを数件だけ載せる方針にします。

初期方針:

- メイン表示は最大3件程度。
- 本人が選んだレビューだけを表示する。
- レビュー元のラベルは自由記述にする。
- アプリ側が勝手にレビュー種別を決めない。

表示例:

```text
受講生 Aさん
出店者 Bさん
クライアント Cさん
参加者の声
お客様の声
```

出さないもの:

- 個人名や連絡先。
- 受講者情報。
- 課題内容。
- 支払い情報。
- 内部メモ。

レビューをどこで選ぶかは、今後の検討事項です。

候補:

- 各アプリ側で「Storyに載せる」を選ぶ。
- Story設定側で、集まったレビューから選ぶ。
- 手動レビューとしてStory側に直接追加する。

## 8. ご依頼・リンク

Storyには、できることメニューとリンク集を置けるようにします。

想定:

- Orderへの制作依頼入口。
- Sessionへの予約・相談入口。
- Academyの公開講座入口。
- Eventの公開イベント入口。
- Communityの参加入口。
- ショップページ。
- ホームページ。
- SNS。
- その他リンク。

できることメニューの方針:

- 仕事の入口としてわかりやすいカード型にする。
- アプリ由来のメニューと、自由記述メニューの両方を想定する。
- リンクなしの説明だけにするか、必ずリンクを持たせるかは今後相談する。
- 表示ON/OFFと表示順を持つ。

## 9. 公開中の講座 / イベント

AcademyやEventなど、公開フロントを持つアプリは、Storyから入口を置けるようにします。

ただし、以下は自動表示しません。

- 非公開講座。
- 内部向けイベント。
- 参加者情報。
- 申込者情報。
- 詳細なスケジュール。
- 支払い情報。

表示する場合も、本人が公開ONにしたものだけを表示します。

## 10. つながるボタン

Storyには、相手とつながるための入口を置けるようにします。

想定:

- つながる。
- 問い合わせる。
- 相談する。
- QRで共有する。

重要な方針:

- つながった人の一覧は本人だけが見られる管理情報にする。
- 公開Story上に「誰とつながっているか」は出さない。
- 顧客、受講者、会員、依頼者の一覧を外部公開しない。

## 11. QRコード

Storyは、QRコードで見せられることを前提にします。

機能候補:

- Story URLのQRコード表示。
- QRコード保存。
- QRコード共有。
- 名刺やチラシに載せやすい形式。

将来的には、紙の名刺の代わりにStoryを見せてつながる流れを目指します。

## 12. 表示ON/OFF管理

Storyでは、表示ON/OFF管理を必須にします。

ON/OFFが必要なもの:

- プロフィール項目。
- 得意なことタグ。
- 受付中ステータス。
- 活動サマリー全体。
- 活動サマリーの各数字。
- 作品ポートフォリオ全体。
- 作品ごとの表示。
- 口コミ全体。
- 口コミごとの表示。
- ご依頼・リンク全体。
- リンクごとの表示。
- 公開講座 / イベント。
- QRコード。
- つながるボタン。

表示ラベルも本人が変更できるようにします。

理由:

- MarketNoteを出店管理以外に使う人がいる。
- SessionやOrderの使い方も人によって違う。
- 同じ数字でも `出店回数` `主催回数` `活動回数` など、自然な見せ方が変わる。

## 13. Storyに出さないもの

Storyに自動表示しないもの:

```text
細かなActivity Logの時系列
出店予定や移動予定
詳細なスケジュール
売上金額
経費金額
請求情報
領収書情報
支払い情報
顧客情報
受講者情報
生徒情報
会員情報
学校情報
課題内容
評価内容
学習進捗
内部メモ
Mikke IDなどの内部管理ID
つながった人の一覧
```

Storyに出すのは、本人または事業者が公開してよいと判断した情報だけです。

## 14. DESKとの関係

DESKは、Storyとは別の役割です。

DESKで扱うもの:

- mikkeOS内の各アプリから来る売上。
- mikkeOS内の各アプリから来る経費。
- 報酬、外注費、会費、更新料などの金額ログ。
- 手動追加・編集した収支。
- 月次、年次の数字。
- 請求書、領収書。
- CSV出力。

DESKは今すぐ本格会計アプリにはしません。

ただし、将来的に以下は検討できます。

- メール文章などの定型文。
- タスク管理。
- Googleカレンダー連携。
- 事務まわりのテンプレート。

## 15. データの持ち方

Story Profileは、複数の情報を組み合わせて作ります。

想定データ:

```text
Storyプロフィール設定
Story表示ON/OFF設定
Activity Logから作る集計値
Item Studioから選んだ作品
手動追加した作品
選択したレビュー
手動追加したレビュー
各アプリの公開フロントリンク
各アプリの受付ステータス
外部リンク
QRコード用の公開URL
```

Activity Logは、Storyの材料にはなりますが、Storyそのものではありません。

## 16. 現在の実装との差分

現在の `components/mikkeos/StoryProfile.tsx` は、まだ公開活動タイムライン寄りの仮実装です。

今後置き換えるべき点:

- `Mikke ID` 表示を公開Storyから外す。
- Activity Logの時系列表示をStoryの中心にしない。
- 活動サマリー、作品、口コミ、リンク、QRを中心にする。
- 作品やレビューは本人が選ぶ。
- 詳細ログや予定は自動公開しない。
- 表示ON/OFFとラベル編集を前提にする。

Supabase Story読み取りテスト枠は、技術検証用として残してよいです。ただし、通常のStory表示とは別物として扱います。

## 17. 実装ステップ案

### Step 1: Story Profileの静的UI再設計

- 参考画像に近いスマホ中心レイアウトを作る。
- まずはmock / localStorageベースでよい。
- Supabase通常接続はまだ行わない。

### Step 2: Story設定モデルを整理

- セクションON/OFF。
- ラベル編集。
- 得意なことタグ。
- 表示順。
- 作品選択。
- レビュー選択。
- リンク設定。

### Step 3: Item Studioポートフォリオ連携

- Item Studioの作品から、Storyに載せたいものだけ選べるようにする。
- 商品登録ログをそのままStoryに流さない。

### Step 4: 活動サマリー集計

- Activity Logから集計値を作る。
- 表示ラベルはStory側で変えられるようにする。
- 各数字ごとにON/OFFを持たせる。

### Step 5: 受付ステータス連携

- Order / Session / Academy / Event / Community の受付状態をStoryに反映する。
- Story側では表示ON/OFFとラベル編集だけを持つ。

### Step 6: レビュー選択

- 各アプリ由来または手動レビューから、公開するものだけ選ぶ。
- レビュー元ラベルは自由記述にする。

### Step 7: QRコードとつながる機能

- Story公開URLのQRコードを出す。
- つながるボタンを置く。
- つながった人の一覧は本人専用の管理画面で見る。

### Step 8: Supabase本接続

- Story設定、作品選択、レビュー選択、リンク設定などの安全なモデルが固まってから行う。
- Activity Logの `Story素材候補` を直接公開タイムラインにしない。
- 金額ログ、個人情報、予定情報をStoryに混ぜない。

## 18. まだやらないこと

今回は方針メモであり、以下はまだ行いません。

```text
/story 通常表示のSupabase本接続
/desk 通常表示のSupabase本接続
/os 通常表示のSupabase本接続
/log 通常表示の完全Supabase化
各アプリ保存の一斉Supabase化
DBマイグレーション
RLS / policy / constraint変更
Mikke IDの公開表示
Activity Logの公開タイムライン化
予定やスケジュールの自動公開
金額ログのStory公開
個人情報のStory公開
```

## 19. 次の実装候補

次に実装へ進むなら、最初は `/story` のmock UIを参考画像に寄せるのがよいです。

ただし、その時も以下を守ります。

- 通常表示はまだSupabase本接続しない。
- 既存の技術テスト枠は消さない。
- Storyは公開Activity Log一覧にしない。
- 表示ON/OFFを前提にする。
- Mikke IDは公開しない。
