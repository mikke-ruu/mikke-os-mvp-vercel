# MIKKEOS Manager M2 受信箱設計

作成日: 2026-07-18
対象: N2 / Manager M2-e

## 結論

Managerには「他の人や他のアプリから届いた依頼を受け取る場所」として、受信箱の席を確保する。

ただし、M2では画面・保存処理・承認処理は実装しない。実装は Page PG-4「他者掲載依頼」と同時に行う。

## 受信箱の役割

Managerは巨大なOS入口ではなく、個々のアプリで進んでいることを横断して見られる場所にする。

受信箱はその中でも、本人の返事が必要な依頼だけを受け取る場所。

```text
個々のアプリで作業が進む
↓
他者から本人確認・掲載許可・販売委託などの依頼が届く
↓
Manager受信箱に「返事が必要なもの」として出る
↓
本人が承認または辞退する
↓
承認後だけ相手側・掲載先・販売導線に効果が出る
```

## 最初のユースケース

### Page掲載依頼

他人のStory / Item Studio作品などを、あるPageに掲載したいときに使う。

```text
依頼者: Pageの管理者
宛先: 掲載される本人のmikkeID
返事: 承認 / 辞退
効果: 承認後だけPage側に掲載される
```

### セレクトショップ販売委託

掲載依頼に販売条件が含まれる場合は、掲載許可と販売委託を1つの承認として扱う。

```text
提示されるもの:
- 何を掲載するか
- どのPage / ショップに載せるか
- 販売条件
- 報酬または分配条件
- いつまで有効か

本人ができること:
- 承認する
- 辞退する
```

条件は依頼者側が提示し、本人は承認または辞退する。受信箱の中で条件交渉UIは作らない。

## 型の予約

M2-eでは、実装前の予約として `ManagerInboxItem` を追加する。

```text
更新: lib/manager/types.ts
```

予約する主な項目:

```text
requestKind: page_listing_request / select_shop_delegation
title
description
requesterLabel
receivedAt
status: pending / accepted / declined / expired
source
primaryActionLabel
secondaryActionLabel
consentSummary
expiresAt
```

この型はM2時点では未使用の予約。保存先・一覧画面・承認処理はまだ作らない。

## 画面方針

文言は「管理」ではなく、利用者が受け取りやすい言葉に寄せる。

```text
使う:
受信箱
届いた依頼
確認する
承認する
辞退する
返事が必要

避ける:
管理します
監視します
強制連携
自動掲載
```

## 課金・招待の扱い

受信箱に依頼が届いた側へ、いきなり課金壁を出さない。

Page掲載依頼や販売委託は、まず「依頼を受け取って返事をする」体験にする。オーナー側のプラン・手数料・販売条件は、依頼を出す側の責任として扱う。

## 禁止事項

M2では次を行わない。

```text
Manager受信箱ルートの新設
受信箱UIの表示
localStorage保存
Supabase保存
RLS変更
通知実装
承認/辞退による外部アプリ更新
Page PG-4の前倒し実装
```

## PG-4実装時の受け入れ条件

PG-4で実装する時は、少なくとも次を満たす。

```text
本人宛の依頼だけが見える
依頼内容・依頼者・掲載先・条件が確認できる
承認するまで掲載・販売委託の効果が出ない
辞退した依頼は掲載先に反映されない
期限切れ依頼は承認できない
承認/辞退の履歴が後から確認できる
招待された側に課金壁を出さない
```

## 次に進める条件

M2-eとしては、次の状態で完了とする。

```text
受信箱の役割が明文化されている
Page PG-4との依存関係が明記されている
セレクトショップ販売委託との関係が明記されている
ManagerInboxItemの型予約がある
M2では実装しない範囲が明記されている
```
