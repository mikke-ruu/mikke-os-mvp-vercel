## 1. この画面設計の前提

Libraryは、mikkeOS内の「一時編集場所」と「自分用の書庫」を兼ねるアプリとする。
Academy、Page、Fund、Item Studio、Order、Team Worksなどへ入れる前の文章、説明、構成、提出物、URL、メモ、AI相談文を整理する。

初期実装では、他アプリへ自動送信しない。
完成した文章や構成をコピーし、利用者が各アプリ側へ貼り付ける。

保存は段階的に扱う。

- Free: 端末内保存、JSON書き出し/読み込み
- Pro: 将来のMikke ID同期、複数端末利用

UIはmikkeOS共通デザインに寄せる。
独自のネイビーやオレンジは追加せず、`--mikke-*` トークンと固定カラーを使う。

## 2. 画面全体の考え方

Libraryは「大きなダッシュボード」ではなく、日常的に開いてすぐ使う作業台として設計する。

優先する体験:

- すぐ書ける
- あとで見つけられる
- 原文、AI文、整え文、修正版、完成稿を混ぜずに扱える
- 必要なカードだけを組み合わせて提出物名の成果物にできる
- 他アプリを開き直すストレスを減らす
- Free利用者にも保存状態とバックアップ状態がわかる

避ける体験:

- 最初から機能説明が多すぎる
- すべてがカード化された重いホーム
- 細かすぎるステータス管理
- 自動連携しているように見える表現
- Story、DESK、Activity Logへ保存されるように誤解される表現

## 3. 共通UI構造

### 3.1 PC

PCは `MikkeAppShell` を使う。
左にアプリ共通メニュー、中央にLibraryの作業領域を置く。

基本構造:

```text
┌────────────────────────────────────────────────────────────┐
│ mikkeOS common header / app menu                           │
├──────────────┬─────────────────────────────────────────────┤
│ Library nav  │ Active Library screen                       │
│              │                                             │
│ Home         │ Search / actions                            │
│ Library      │ Main content                                │
│ Quick memo   │ Detail / editor / preview                   │
│ Favorites    │                                             │
│ New          │                                             │
│ Folders      │                                             │
│ Templates    │                                             │
│ Backup       │                                             │
└──────────────┴─────────────────────────────────────────────┘
```

PCでは、Team WorksなどからLibraryを開く場合は新しいタブを推奨する。
画面内で2アプリを無理に埋め込まず、ブラウザやOSの左右分割を使える導線にする。

### 3.2 スマホ

スマホは下部アイコンメニューを使う。

下部メニュー:

```text
Home / Library / Memo / Favorites / New
```

中央の `New` はORANGEの主要操作にする。
文字だけの大きいボタンではなく、アイコンと短いラベルで扱う。

他アプリからLibraryを開いた場合だけ、上部に往復スイッチを表示する。

```text
Team Works  <->  Library
```

Library単体で開いた場合は、このスイッチを表示しない。

## 4. Home

### 4.1 目的

Homeは、Library内の現在地をすばやく把握し、すぐ作業へ戻る画面。
あいさつや説明を主役にしない。

### 4.2 表示内容

```text
LIBRARY
考えたことを、使える形へ。

[検索]

RECENT
最近使ったテーマ

NEXT
次の行動があるもの

QUICK MEMO
受け箱の最新メモ

BACKUP
この端末に保存中 / 最終バックアップ
```

### 4.3 主要操作

- 新規テーマ
- クイックメモを書く
- JSONを書き出す
- JSONを読み込む
- 最近のテーマを開く
- 次の行動があるテーマを開く

### 4.4 PCレイアウト

検索を最上部に置き、その下を2カラムにする。

左:

- Recent
- Quick Memo

右:

- Next
- Backup

情報量は少なめにする。
カードは使ってよいが、角丸と影は控えめにする。

### 4.5 スマホレイアウト

1カラム。
検索、Recent、Next、Quick Memo、Backupの順。
各行はタップしやすい高さを確保する。

## 5. Library一覧

### 5.1 目的

テーマを探して開く画面。
「何を書いたか」だけではなく、「次にどうするか」が見えるようにする。

### 5.2 一覧項目

各テーマに表示する情報:

- タイトル
- フォルダ
- タグ
- ステータス
- 次の行動
- 更新日
- お気に入り

タイトルは提出物名、記事名、講座名、ページ名など、実際の成果物名を主役にする。
アプリ名や案件名はフォルダ、タグ、関連情報として扱う。

例:

```text
新しい講座企画案
Folder: Team Works
Tag: 認定講座リニューアル
Status: 作業中
Next: 確認する
```

### 5.3 検索対象

- テーマタイトル
- 文章カードタイトル
- 文章カード本文
- タグ
- フォルダ
- URL

### 5.4 フィルター

初期実装で必要なもの:

- フォルダ
- ステータス
- 次の行動
- お気に入り

後回し:

- 文章カード分類ごとの絞り込み
- 更新者
- 高度な期間指定

### 5.5 PCレイアウト

PCでは一覧と詳細の中間密度にする。
表のように詰めすぎず、カード一覧のように重くしすぎない。

```text
Search / filters / New

Title                         Status   Next      Folder      Updated
新しい講座企画案              作業中   確認する  Team Works  07/31
Page用プロフィール文          保留     自分で修正 Page        07/30
```

### 5.6 スマホレイアウト

スマホは1列。
タイトル、ステータス、次の行動、フォルダを優先する。
タグが多い場合は先頭1つだけ表示し、残りは件数で示す。

## 6. 新規テーマ作成

### 6.1 目的

最初の保存を軽くする。
タイトルだけでも作れる。

### 6.2 入力項目

必須:

- タイトル

任意:

- フォルダ
- タグ
- ステータス
- 次の行動
- テンプレート

初期値:

```text
Status: アイデア
Next: なし
Favorite: OFF
```

他アプリから開いた場合の候補:

```text
Folder: 呼び出し元アプリ名
Tag: 呼び出し元の案件名またはページ名
```

自動入力ではなく、候補として表示する。

## 7. テーマ詳細

### 7.1 目的

テーマの中にあるカードを見ながら、文章や構成を作る画面。

### 7.2 画面構造

```text
Back / Title / Favorite / More
Status / Next action / Folder / Tags

Actions:
Add block / Compare / Composition / Copy

Blocks:
- memo
- text
- AI consult
- URL
- task
```

### 7.3 ヘッダー

タイトルは大きすぎない。
作業画面なので、ヘッダーは固定または準固定にし、ステータス変更と主要操作へすぐ届くようにする。

表示:

- タイトル
- お気に入り
- 保存状態
- ステータス
- 次の行動

### 7.4 カード一覧

カードは並び替えできる。
初期実装ではドラッグが難しければ、上下ボタンでもよい。

カード共通操作:

- 編集
- 複製
- 削除
- 上へ
- 下へ
- 構成に使う

カードの削除は即消しではなく、確認を挟む。
将来はゴミ箱へ拡張できるようにする。

## 8. 文章カード

### 8.1 目的

原文、AI文、整え文、修正版、完成稿を利用者が把握できるようにする。

### 8.2 分類チップ

固定候補:

- 原案
- AI文
- 整え文
- 修正版
- 完成稿
- 引用
- 自由入力

分類は必須にしない。
ただし、同じテーマ内に複数の文章カードがある場合は、分類チップが見えるようにする。

### 8.3 保存操作

文章編集時の選択:

- このカードを上書き
- 新しい文章カードとして保存

AI文を戻す場合も、原案を上書きしない。
利用者が上書きを選んだ時だけ上書きする。

### 8.4 表示密度

本文プレビューは長くしすぎない。
一覧では先頭数行だけを表示し、本文全体は展開または編集画面で見る。

## 9. クイックメモ / 受け箱

### 9.1 目的

分類前の考え、URL、思いつき、音声文字起こしの貼り付けなどを受ける場所。

### 9.2 操作

- メモを書く
- 既存テーマへ移動
- 既存テーマへコピー
- 新規テーマにする
- 削除

### 9.3 画面

```text
QUICK MEMO
[入力欄]
[保存]

Inbox
- メモ本文
- 作成日
- 移動 / コピー / 新規テーマ / 削除
```

スマホでは、下部メニューのMemoから即入力できるようにする。

## 10. 構成

### 10.1 目的

テーマ内のカードを選び、並べ、提出物や公開文にする。

構成はカード本文を複製しない。
どのカードをどの順で使うかを持つ。

### 10.2 構成画面

```text
Composition: Team Works提出用

Left: 使用カード
Right: Preview

[カードを追加]
[並び替え]
[見出しを含める]
[プレーンテキストをコピー]
[Markdownをコピー]
[テンプレートとして保存]
```

### 10.3 出力

初期実装ではコピーのみ。

- プレーンテキスト
- Markdown

出力先アプリ名は必須指定しない。
ただしテンプレート名として `Team Works提出用`、`Page掲載用`、`Academy講座説明用` などは使える。

## 11. 構成テンプレート

### 11.1 目的

毎回同じ流れで作る提出物、投稿、説明文の下敷きを保存する。

### 11.2 重要なルール

テンプレートは、過去の本文をコピーするものではない。
役割、順番、見出し、出力ルールを保存する。

適用時は、空カードを大量に作らない。
候補カードと不足スロットを表示し、利用者が必要なものだけ追加する。

### 11.3 初期テンプレート候補

- 提出物を作る
- Page掲載文を作る
- Academy講座説明を作る
- Fundプロジェクト文を作る
- Item Studio作品説明を作る
- Order返信文を作る
- AI相談セット

## 12. 比較モード

### 12.1 目的

原案とAI文、整え文と修正版などを比較する。

### 12.2 PC

PCは2ペイン。

```text
Compare

Left: 原案
Right: AI文

[Aを変更] [Bを変更]
[左をコピー] [右をコピー]
[この内容から新しい文章カードを作る]
```

ペイン幅は調整できるとよい。
初期実装で幅調整が重い場合は固定2カラムでよい。

### 12.3 スマホ

スマホは切り替え。

```text
[原案] [AI文]

Card title
Classification
Text body
```

A/Bそれぞれのスクロール位置を保持する。
切り替えても同じ場所へ戻れるようにする。

## 13. 他アプリとの行き来

### 13.1 基本

Libraryは各アプリのメニューに任意表示できるようにする。
ただし初期実装では、データを自動で受け渡さない。

扱う状態:

- 呼び出し元アプリ名
- 呼び出し元URL
- 呼び出し元の表示名
- Libraryで最後に開いたテーマ
- スクロール位置
- 未保存入力

### 13.2 PC

PCでは「新しいタブでLibraryを開く」を用意する。
利用者はTeam Works、Academy、PageなどとLibraryを左右に並べられる。

### 13.3 スマホ

スマホでは上部の往復スイッチで切り替える。

```text
Academy  <->  Library
Page     <->  Library
Team Works <-> Library
```

呼び出し元へ戻る時は、元URLへ戻す。
Library側で入力途中の場合は、切り替え前に自動保存を試みる。

## 14. Backup / Settings

### 14.1 表示

Backup画面では、Free利用者にも状態がはっきり見えるようにする。

表示:

- 保存先: この端末
- 最終保存
- 最終JSONバックアップ
- 未バックアップの変更件数
- 使用容量の目安

### 14.2 操作

- JSONを書き出す
- JSONを読み込む
- 読み込み前に現在データの緊急バックアップを作る
- 保存状態を確認する

### 14.3 文言

Freeを「自己責任」と突き放す表現にはしない。
ただし、端末やブラウザのデータ削除で消える可能性は明示する。

表示例:

```text
この端末に保存されています。別の端末で使う場合はJSONバックアップを書き出してください。
```

## 15. 空状態


### 15.2 Quick Memo空状態

```text

```

### 15.3 Composition空状態

```text

テーマ内のカードから選んで追加できます。
```

## 16. エラー状態

### 16.1 保存失敗

保存に失敗した場合は、赤系ではなくORANGEまたはPINKの補助表示で落ち着いて知らせる。
本文が消えないよう、画面内の入力値は保持する。

表示:

```text
保存できませんでした。入力内容はこの画面に残っています。
```

### 16.2 JSON読み込み失敗

表示:

```text
このJSONは読み込めませんでした。ファイル形式を確認してください。
```

### 16.3 容量不足

表示:

```text
この端末の保存容量が少なくなっています。JSONバックアップを書き出してください。
```

## 18. 初期実装で触る可能性が高い場所

実装時に確認して決める。
現時点の候補:

- `app/apps/library/page.tsx`
- `components/library/`
- `lib/library/`
- `lib/mikkeos/apps.ts`
- `lib/mikkeos/routes.ts`
- `lib/mikkeos/app-actions.ts`
- `components/mikkeos/`

既存のAcademy、Page、Team Works、Story、DESKのDBや保存処理は初期実装で触らない。
共通メニューへ表示する場合も、最小の登録変更だけにする。

## 19. 受け入れ条件

L1画面実装の受け入れ条件:

- `/apps/library` を開ける
- PCでHome、一覧、テーマ詳細、構成、比較が破綻しない
- スマホで下部ナビと切り替え比較が使える
- 新規テーマをタイトルだけで作れる
- 文章カードを分類チップつきで作れる
- 原案を上書きせずAI文を別カードとして残せる
- 構成プレビューからコピーできる
- クイックメモをテーマへ移動またはコピーできる
- JSONを書き出し、読み込み前の確認が出る
- Freeの保存先とバックアップ状態が見える
- 他アプリへの自動送信があるように見えない
- Activity Log、Story、DESKへ保存されるように見えない
- `npm.cmd run lint` が通る
- `npm.cmd run build` が通る
- 375px、768px、1280pxで文字やボタンがはみ出さない

## 20. 実装前の最終確認

この画面設計で、実装前に決めるべきことは少ない。
残る判断は実装時に既存コンポーネントを見ながら決める。

優先する判断:

- `MikkeAppShell` にLibraryをどう登録するか
- IndexedDB用の軽量ラッパーを新規に作るか、既存localStorageパターンから始めるか
- アイコンは既存のlucide利用状況に合わせる
- 初期サンプルデータを入れるか、空状態から始めるか

おすすめ:

最初は空状態 + 1つの作成済みデモテーマを用意する。
ユーザーが何も入れていない状態の見え方と、実際に作業がある状態の両方を確認できるため。
