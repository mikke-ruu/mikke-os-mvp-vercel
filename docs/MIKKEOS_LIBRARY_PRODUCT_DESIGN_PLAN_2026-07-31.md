## 1. プロダクト定義

Libraryは、単なるメモ帳やファイル置き場ではない。

文章、アイデア、AI相談、URL、資料、タスクなどをテーマ単位で集め、
足したり、引いたり、並べ替えたりしながら、後で使える成果物へ整える
**個人用の編集書庫・構成作業台**である。

主な利用場面:

- Team Worksの提出物を作る前に、材料と文章を整理する
- Academyの講座、教材、企画の構想を立てる
- Pageに掲載する文章を組み立てる
- 毎回行う投稿や案内作成のルーティンをテンプレート化する
- 過去の文章、AI回答、定型文、参考URLを再利用する
- 思いついた内容をクイックメモへ入れ、後からテーマへ整理する

LibraryはStoryやDESKの下位機能ではない。
Library内の文章や内部メモをStoryやDESKへ自動送信しない。

## 2. 設計原則

1. 最初はタイトルだけでも作れる軽さを守る。
2. 原文、AI文、整え文などを、利用者が必要な分だけ残せる。
3. 上書き保存と、別カードとして残す保存の両方を選べる。
4. 他アプリへ無理に接続せず、第一段階はコピーで完結させる。
5. Freeでも利用者が自分のデータを持ち出せる。
6. Proはデータを開放する料金ではなく、複数端末同期と安心の料金にする。
7. 色、ナビ、余白、角丸、影はmikkeOS共通正典へ合わせる。
8. Library固有の独立CSSや独自パレットを作らない。
9. 文章をActivity Logへ保存しない。節目の事実だけを将来の接続候補にする。
10. 計画、ローカル保存、クラウド同期を段階分けし、一度に作らない。

## 3. 用語

### 3.1 テーマ

Libraryで扱う一つの企画、記事、資料、提出物などのまとまり。
内部名は `LibraryItem` とする。

例:

- 認定講座の構築
- Team Works 7月提出物
- アメブロ記事の再編集
- Page用プロフィール文章

### 3.2 役割カード

テーマの中へ追加する情報単位。
内部名は `LibraryBlock` とする。

標準タイプ:

- アイデア
- 文章
- AI相談
- 定型文
- Bookmark
- Apps
- URL
- ファイル
- Sound
- タスク
- メモ
- カスタム

### 3.3 文章分類

文章カードへ任意で付ける分類チップ。

初期候補:

- 原案
- AI文
- 整え文
- 修正版
- 完成稿
- 引用
- 自由入力

分類は必須にしない。利用者はいつでも変更できる。

### 3.4 構成

一つのテーマ内で「どの役割カードを、どの順番で使うか」を保存したもの。
内部名は `LibraryComposition` とする。

同じテーマから複数の構成を作れる。

例:

- Team Works提出用
- AI相談用
- Page掲載用
- 自分の確認用

### 3.5 構成テンプレート

毎回使う役割、順番、見出し、コピールールを保存した雛形。
内部名は `LibraryCompositionTemplate` とする。

構成テンプレートは特定テーマの文章を複製するものではない。
新しいテーマへ適用した時に、空の構成または必要な役割カード候補を作る。

例:

```text
週次報告テンプレート

1. 今週行ったこと
2. 成果
3. 課題
4. 次に行うこと
5. 参考URL
```

### 3.6 クイックメモ / 受け箱

分類先を決めずに、文章やURLを一旦保存する場所。
後から次の操作ができる。

- 新しいテーマにする
- 既存テーマへ移動する
- 既存テーマへコピーする
- 不要なら削除する

### 3.7 参照

別テーマの役割カードを、内容を複製せず利用する関係。

参照元が変わっても即時に本文を置き換えず、
「参照元に更新あり」と表示し、利用者が更新または固定を選ぶ。

## 6. mikkeOSアプリ間の移動

## 6.1 共通アプリメニュー

Libraryは `MikkeAppShell` / `MikkeOwnerMenu` のアプリ一覧へ追加できるようにする。
表示は利用者の権限または設定に従い、任意とする。

PC:

- 「Libraryを開く」
- 「Libraryを新しいタブで開く」
- 新しいタブで開き、OSやブラウザの左右分割を利用できる
- 元アプリとLibraryの最後に開いていた場所をそれぞれ保持する

## 6.2 スマホ往復スイッチ

Team WorksなどのアプリからLibraryを開いた場合、呼び出し元を保持する。

例:

```text
Team Works  ⇄  Library
Academy     ⇄  Library
Page        ⇄  Library
```

ヘッダーまたは共通アプリ切り替えシートから、比較モードのように
二つの画面を切り替えられるようにする。

第一段階では画面の同時表示や埋め込みは行わない。
それぞれのURL、テーマID、スクロール位置、未保存入力を可能な範囲で保持し、
往復しても作業場所を見失わないことを優先する。

## 7. 保存設計

## 7.1 Free

通常保存:

- IndexedDB
- 端末 / ブラウザ / Libraryのorigin単位
- 自動保存
- 保存失敗と容量不足を検知
- Persistent Storage APIを利用可能な環境では永続化を要求

画面へ常時表示する情報:

- 保存先: この端末
- 最終保存日時
- 最終バックアップ日時
- 未バックアップの変更件数または経過日数

Freeの制約:

- 複数端末の自動同期なし
- JSONによる手動移行
- 端末やブラウザのデータ削除で消える可能性がある
- シークレット / プライベートモードを正式な保存環境にしない

## 7.2 JSONバックアップ

JSONへ含める:

- テーマ
- 役割カード
- 文章分類
- フォルダ
- タグ
- 構成
- 構成テンプレート
- タスク
- 参照関係
- プロンプト定型文
- Library設定

メタ情報:

- `format`
- `schema_version`
- `exported_at`
- `app_version`
- 件数
- チェック情報

バックアップ操作:

1. データ整合性を確認
2. JSON生成
3. ファイル保存
4. 最終バックアップ日時更新

復元操作:

1. ファイル形式とバージョン確認
2. 件数と内容の概要を表示
3. 「置き換える」または「追加する」を選択
4. 復元前に現在データの緊急バックアップを作る
5. 一つのトランザクションとして復元
6. 成功件数と失敗件数を表示

添付ファイルは第一段階のJSONへ埋め込まない。
添付が対象外であることをバックアップ画面へ明記する。
完全バックアップは将来のZIP対応とする。

## 7.3 Pro

通常保存:

- Supabase Database
- Supabase AuthのMikke IDへ紐づける
- 添付ファイルは将来Supabase Storageへ保存
- スマホ、PC、タブレットで同期

FreeからProへの移行:

1. ローカルデータ件数を表示
2. クラウドへ移す内容を確認
3. ローカル緊急バックアップを作成
4. Supabaseへアップロード
5. 件数とID対応を検証
6. 同期モードへ切り替える
7. ローカルキャッシュはオフライン表示用に残す

初回のPro同期では、複雑な自動マージを行わない。
端末とクラウドの両方に既存データがある場合は、
内容、件数、更新日時を表示して利用者に選択させる。

ProでもJSON書き出しと復元を残す。
Supabase側のサービスバックアップだけを、利用者向け復元機能として扱わない。

## 7.4 Free / Pro境界

| 機能 | Free | Pro |
| --- | --- | --- |
| テーマ・役割カード | あり | あり |
| 構成・テンプレート | あり | あり |
| 検索・コピー | あり | あり |
| 端末内自動保存 | あり | キャッシュとしてあり |
| JSON書き出し・復元 | あり | あり |
| 複数端末自動同期 | なし | あり |
| クラウド復元 | なし | あり |
| Storage添付 | 将来検討 | 将来対応 |

基本的な編集機能をPro限定にしない。

## 8. 概念データモデル

実装時に既存の命名規則と実DBを確認して確定する。

### 主テーブル候補

- `library_items`
- `library_blocks`
- `library_block_fields`
- `library_folders`
- `library_tags`
- `library_item_tags`
- `library_compositions`
- `library_composition_blocks`
- `library_composition_templates`
- `library_composition_template_slots`
- `library_item_relations`
- `library_block_references`
- `library_tasks`
- `library_prompt_templates`

### 重要な設計判断

- 役割は `library_items` へ重複保存せず、blocksから導出する。
- タスクは自由JSONだけにせず、期限、優先度、完了日時、Manager表示を構造化する。
- 並び順は整数で保持する。
- 削除は将来のゴミ箱を考慮し `deleted_at` を持てる形にする。
- カスタムフィールドは型、ラベル、値、並び順を分ける。
- 構成はカード本体を複製せず参照する。
- 構成テンプレートは特定テーマの本文を保持しない。
- Pro用テーブルは所有者を判定できる `user_id` を持つ。
- RLSで利用者本人のデータだけを読み書きできるようにする。
- UPDATE policyには既存行の `USING` と更新後行の `WITH CHECK` の両方を設定する。
- 公開用viewを第一段階で作らない。

## 9. Manager連携

タスクカードはLibraryを正本とする。
Managerへタスク本文をコピーしない。

Managerへ表示する条件候補:

- Manager表示がON
- 未完了
- 期限または次の行動がある

Managerで表示する内容:

- タスク名
- テーマ名
- 期限
- 優先度
- Libraryへのリンク

Manager側で完了した場合も、Libraryの同じタスクを更新する。

第一段階のLibrary本体が安定するまでManager接続は行わない。

## 10. Activity Log境界

MVPではActivity Logへ接続しない。

将来候補:

- テーマを完成にした
- 構成を成果物として確定した
- 外部公開や提出を利用者が明示的に記録した

記録する場合も初期値は:

- private
- Story対象外
- DESK対象外
- 金額なし

文章本文、内部メモ、AI相談、参照URL、タスク詳細をActivity Logへ入れない。

## 15. 第1回設計合意

次の方針を確定する。

1. Freeの初期版では、添付ファイルカードにURLとファイル情報を保存する。実ファイル本体の端末保存は後段とする。
2. 構成テンプレート適用時は空カードを大量に自動作成せず、必要カード候補を表示して利用者が追加する。
3. 別テーマ参照はL3後半へ配置し、構成とテンプレートの基本操作を先に完成させる。
4. スマホ往復スイッチはLibraryを他アプリから開いた時だけヘッダーへ表示する。Libraryを単独で開いた時は表示しない。

## 17. mikkeOS共通編集レイヤー

Libraryは、各アプリの本番データを直接編集する場所ではない。
各アプリへ入力・掲載・提出する前に、文章、構成、説明、定型文を一時編集する
共通の作業場所として使う。

```text
考える・集める・比較する・整える
                ↓
              Library
                ↓
       コピーして各アプリへ入力
```

各アプリはそれぞれの正本を持つ。
Libraryは正本へ自動送信せず、利用者が選んだ完成文だけをコピーできるようにする。
